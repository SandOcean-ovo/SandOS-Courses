# 阶段 1：排错记录

> 记录阶段 1 实际遇到的问题、现象、定位过程和修复。这些都是真实发生过的，适合直接改写成教材中的“常见失败现象”。

## 1. QEMU 启动后完全没有输出

**现象**：链接成功，`qemu-system-arm ... -kernel build/sandos.elf` 运行 10 秒没有任何输出，也没有崩溃。

**定位过程**：

1. 先排除向量表：`arm-none-eabi-objdump -h` 看到 `.text` 在 `0x0`，`nm` 看到 `g_vectors` 在 `0x0`、`Reset_Handler` 在 `0x158`，布局正常。
2. 用 GDB 连接 QEMU（`-S -gdb tcp::1234`）：`break Reset_Handler` 能停住，`break __libc_init_array` 也能停住，但 `break main` 永远不触发。
3. 反汇编 `__libc_init_array`，看到它调用 `_init`（地址 `0x17e8`）。`objdump -d -j .init` 显示 `_init` 里只有 `push {r3-r7, lr}` 和 `nop`，**没有返回指令**，CPU 顺着往下执行到不知名的位置。

**原因**：`_init` 由 `crti.o` 和 `crtn.o` 共同拼成：`crti.o` 提供 `push` 开头，`crtn.o` 提供 `pop {…}` 和 `bx lr` 结尾，二者都放在 `.init` 段里，要靠链接器按**输入顺序**拼接。我最初的链接脚本只收集了 `.init_array`，没有写 `.init`、`.fini`，链接器把它们当作孤立段自动放置。

**重现验证**：删掉链接脚本中 `KEEP(*(.init))`/`KEEP(*(.fini))` 重新链接，`.init` 段只有 4 字节，`_init` 里只剩 `push {r3-r7, lr}` 和 `nop`，**缺少后半段的 `pop` 与 `bx lr`**，所以返回后 CPU 顺着往下执行。现行脚本下的 `_init` 则是完整的：`push … nop … pop … pop {r3} … mov lr, r3 … bx lr`。
我没有进一步核实为什么孤立段放置会丢掉 `crtn.o` 那一半（可能与 `--gc-sections` 有关，`--no-gc-sections` 的对照因另一个缺失符号 `__bss_end__` 没能链接成功），所以“链接器内部为什么这样做”不做断言，只记录“这样写会坏、那样写不会坏”。

**修复**：在 `.text` 输出段内加入 `KEEP(*(.init))` 和 `KEEP(*(.fini))`，并把 `.init_array` 单独放一个输出段。修复后 `_init` 反汇编里出现了 `pop {r3, r4, r5, r6, r7}` 和 `pop {r3}`，`main` 能到达。

**教训**：QEMU 没有输出时，不要猜串口配置。先用 GDB 看 CPU 停在哪，一般几分钟就能定位。

## 2. 链接报 `undefined reference to 'end'`

**现象**：

```
libnosys.a(sbrk.o): in function `_sbrk':
(.text._sbrk+0x18): undefined reference to `end'
```

**原因**：`--specs=nosys.specs` 带的 `_sbrk` 用符号 `end` 表示堆的起点，而我的链接脚本没有定义它。

**修复**：链接脚本里加 `PROVIDE(end = _ebss); PROVIDE(_end = _ebss);`，让堆从 `.bss` 末尾开始。

## 3. 用 GDB 的命令一直不返回

**现象**：我把 `qemu-system-arm … &` 和 `arm-none-eabi-gdb -batch …` 放在同一条命令里，命令 120 秒超时被转入后台，QEMU 进程残留。

**原因**：GDB 的 `continue` 在 `main` 永远不触发（见第 1 条）时会无限等待，而 QEMU 在后台没有被清理。

**处理**：给 QEMU 和 GDB 都加 `timeout`；用 `taskkill` 清理残留的 QEMU/GDB 进程。以后任何 GDB 批处理命令都必须带 `timeout`。

## 4. Python 读文件报 `UnicodeDecodeError: 'gbk' codec`

**现象**：用 Python 读取含中文的 `link.ld` 时报 `'gbk' codec can't decode byte 0xba`。

**原因**：Windows 下 Python 默认使用系统编码 GBK，而文件是 UTF-8。

**修复**：所有 `open()` 都显式写 `encoding='utf-8'`。批量替换时还要注意 `newline=''`，否则 CRLF/LF 会被悄悄改写，导致“替换没有匹配上”。

## 5. Makefile 的批量替换没有生效

**现象**：给 Makefile 加 `APP` 变量后，所有负例都报 `build/neg_xxx.elf: No such file or directory`。

**原因**：我用字符串替换修改 Makefile，但文件里的换行是 CRLF，匹配字符串里是 LF，头部替换静默失败，只有后半段改成功了，导致 `TARGET` 仍是 `sandos.elf`。同时我用 `grep` 过滤了构建输出，把 `make` 的错误信息也过滤掉了。

**修复**：改用读取时统一换行的方式重写头部，并且不在检查构建结果时用 `grep` 吞掉输出。后来整份重写了 Makefile，并通过 `.gitattributes` 固定为 LF。

## 6. 故意制造的故障没有触发 HardFault

**现象**：最初的 `neg_fault.c` 往 `0xE0000000` 写入以触发总线故障，QEMU 却正常继续，运行脚本判成了通过（`RESULT: PASS`）。

**重现验证**：单独写一个程序依次输出 `before`、对 `0xE0000000` 写 1、输出 `after-write` 和 `TEST:PASS`，在 QEMU 11.1.3 的 `mps2-an385` 上三行都正常输出，没有故障。具体为什么该地址的写入被静默接受，我没有去查 QEMU 源码，不做断言。这说明**负例本身也需要验证**：如果没有这个负例，我会误以为“故障路径已经测过”。

**修复**：改用 `udf #0`（永久未定义指令），它在 Cortex-M3 上一定会产生 UsageFault；UsageFault 默认未使能，会升级为 HardFault。修复后输出 `FAULT: HardFault PC=000001F4 LR=000001E7 xPSR=41000000` 与 `TEST:FAULT`。

## 7. “先 PASS 后故障”被误判为通过

**现象**：`neg_pass_text_only.c` 先输出 `TEST:PASS` 再触发故障，运行脚本一看到 `TEST:PASS` 就立即返回通过，没有等到故障输出。

**原因**：轮询逻辑一旦发现 PASS 就退出，不再观察后续输出。

**修复**：加入观察期 `GRACE = 0.5` 秒：看到 PASS 后再等一会儿，期间出现失败标记则判失败。

**局限**：观察期是固定的 0.5 秒，如果故障发生得更晚，仍可能漏掉。更可靠的做法是让测试程序在输出 PASS 后主动通过 semihosting 退出，这在 TODO 里还没做。

## 8. 同优先级任务的打印顺序不固定

**现象**：冒烟用例两次运行，输出分别是 `A0 B0 A1 B1 A2 B2` 与 `A0 B0 B1 A1 B2 A2`。

**判断**：A、B 优先级相同，同一个 tick 被唤醒时谁先运行取决于延时链表的唤醒顺序。这有可能违反“信号量/延时唤醒保持 FIFO”的契约，也可能只是延时链表的实现细节，**现在无法判断**。

**处理**：冒烟用例只断言偏序（A0→B0→A2），不把现象固定成期望；阶段 2 对照 M1 接口契约再核对，不在阶段 1 擅自改内核。
