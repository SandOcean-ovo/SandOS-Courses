# 阶段 1：新增代码说明

> 说明阶段 1 新增或修改的每个文件**做了什么、为什么这样写、关键细节**。
> 源码里已有 Doxygen 注释写明接口与寄存器用法；本文讲全局关系和设计理由。

## 1. 启动到运行的整体流程

```
复位
 └─ CPU 读向量表：第 0 项 -> MSP，第 1 项 -> PC          (startup.c: g_vectors)
     └─ Reset_Handler：拷贝 .data、清零 .bss             (startup.c)
         └─ __libc_init_array -> main                    (startup.c)
             └─ uart_init；OS_Init；OS_TaskCreate ×2     (main.c)
                 └─ OS_StartScheduler                    (os_core.c，未改)
                     ├─ OS_Init_Timer：配置 SysTick、设置优先级   (os_cpu.c)
                     └─ OS_Schedule：置位 PendSV 挂起位
                         └─ PendSV_Handler：首次启动，恢复第一个任务  (os_cpu_a_gcc.S)

运行期：
 SysTick 中断 -> SysTick_Handler -> OS_Tick_Handler（延时到期则唤醒任务并请求切换）
             -> PendSV_Handler 保存当前任务、恢复下一个任务
```

## 2. 内核移植层改动

### `rtos/Portable/ARM_CM3/os_cpu.h`（修改）

- 把 `#include "stm32f1xx.h"` 换成 `#include "os_board.h"`。
- **原因**：移植层只需要 CMSIS Core（SysTick、NVIC、SCB、`__CLZ` 等）和中断号枚举，并不需要 STM32 的外设寄存器定义。把头文件交给板级目录提供之后，QEMU 与 STM32F103 各自提供 `os_board.h`，内核和移植层代码完全一样。

### `rtos/Portable/ARM_CM3/os_cpu.c`（修改）

- `OS_Init_Timer` 的重载值改为 `(OS_CPU_CLOCK_HZ / 1000U) * ms`。
- **原因**：基线写死 72 MHz，在 QEMU（25 MHz）上 tick 周期会错。
- **细节**：先除后乘，避免 `时钟 × 毫秒` 在 32 位下溢出；要求时钟是 1000 的整数倍，否则有舍入误差。

### `rtos/Portable/ARM_CM3/os_cpu_a_gcc.S`（新增）

- GNU 汇编语法的 `PendSV_Handler`，逻辑与 `os_cpu_a.s` 完全一致。
- **工作原理**：
  1. 进入异常时硬件已把 `xPSR/PC/LR/R12/R3-R0` 压入任务栈（PSP）；
  2. 若 `CurrentTCB` 非空，用 `STMDB` 手动压入 `R4-R11`，把新的栈指针写回 `TCB->stackPtr`；
  3. 把 `CurrentTCB` 更新为 `NextTCB`，从它的 `stackPtr` 弹出 `R4-R11`，写入 PSP；
  4. `LR |= 4`，保证返回到“线程模式 + PSP”；`BX LR` 触发硬件弹栈，开始运行新任务。
- **依赖的约定**：`OS_TCB` 的第一个成员必须是栈指针 `stackPtr`（已在 `os_core.h` 核对）；`CurrentTCB == NULL` 表示首次启动。
- **注意**：全程用 `CPSID I` 关中断保护对 `CurrentTCB/NextTCB` 的修改，结尾 `CPSIE I`。这是异常处理内部的操作，不等同于任务代码里的“临界区恢复”问题。

## 3. 板级文件 `ports/qemu-mps2/`

### `os_board.h`

提供 CMSIS Core 需要的 5 个宏/类型（`IRQn_Type`、`__CM3_REV`、`__MPU_PRESENT`、`__NVIC_PRIO_BITS`、`__Vendor_SysTickConfig`），再包含 `core_cm3.h`，最后定义内核用的 `OS_CPU_CLOCK_HZ = 25000000`。

**需要特别注意**：`__NVIC_PRIO_BITS = 3`。CMSIS 的 `NVIC_SetPriority` 会把优先级左移 `8 - 位数`，再截断到 8 位。`os_cpu.c` 里写的 15 和 14 在 3 位下被截断为 7 和 6，相对顺序（PendSV 最低）仍然成立，但具体数值依赖板子。

### `startup.c`

- **向量表 `g_vectors`**：放在 `.isr_vector` 段，链接脚本保证它位于地址 0。第 14 项是 `PendSV_Handler`，第 15 项是 `SysTick_Handler`。
- **`Reset_Handler`**：拷贝 `.data`、清零 `.bss`、调用 `__libc_init_array`、进入 `main`。
- **`SysTick_Handler`**：只转发给内核的 `OS_Tick_Handler`。上游仓库没有定义它，所以放在板级文件里。
- **`HardFault_Handler`（`naked`）**：根据 `EXC_RETURN` 的 bit2 判断故障时用的是 MSP 还是 PSP，把栈指针和名字作为参数交给 `Fault_Report`。必须是 naked，否则编译器生成的函数序言会改变栈指针，读到的就不是硬件压入的栈帧。
- **`Fault_Report`**：从栈帧取 PC、LR、xPSR 打印，并输出 `TEST:FAULT`。这个标记是测试脚本识别故障的依据。

### `link.ld`

- 布局：Flash 从 `0x00000000`，RAM 从 `0x20000000`。
- `.text` 里把 `.isr_vector` 放最前，并把 `.init`、`.fini` 放进同一个输出段（原因见《排错记录》第 1 条）。
- 提供 `_sidata/_sdata/_edata/_sbss/_ebss/_estack` 给启动代码，以及 `end/_end` 给 newlib 的 `_sbrk`（原因见《排错记录》第 2 条）。

### `uart.c` / `uart.h`

CMSDK APB UART0 的最小发送驱动：基地址 `0x40004000`，写 `BAUDDIV=16`、`CTRL=1` 初始化；发送时轮询 `STATE.bit0`（TX 满）再写 `DATA`。不使用中断。**它是测试框架的输出通道**，测试脚本读的就是它的输出。

### `syscalls.c`

newlib-nano 的 `printf` 最终调用 `_write`。这里把 `_write` 接到 `uart_putc`，遇到 `\n` 先补 `\r`。其余 `_read/_close/_fstat/_isatty/_lseek` 都是返回固定值的桩，只为让链接通过。

### `main.c`（用例 SMOKE-01）

两个同优先级任务各循环 3 次，每次打印后 `OS_Delay(10)`；任务 A 循环结束后打印 `TEST:PASS`。它同时覆盖：启动、UART、首次 PendSV 切换、SysTick 驱动的延时唤醒。

**判定只看偏序**：A、B 同一 tick 被唤醒时打印顺序不固定，所以脚本只要求 `A0 → B0 → A2` 依次出现，不要求 A、B 严格交替。

### `Makefile`

- `APP=<文件>` 选择应用或测试程序，默认 `main.c`；产物名是 `build/<文件名>.elf`。
- 公共文件（`startup.c`、`uart.c`、`syscalls.c`）总是参与；`main.c` 先从通配里排除再追加 `APP`，避免出现两个 `main`。
- 内核直接引用 `../../rtos`，不复制。
- benchmark 默认关闭：`-DOS_BENCHMARK_ENABLE=0`，且不编译 `benchmark.c`（它依赖 DWT，QEMU 不适合测周期）。

## 4. 测试框架 `tests/`

### `scripts/run_qemu.py`

启动 QEMU，后台线程读串口输出，轮询判定。规则：

| 情况 | 结果 | 退出码 |
|---|---|---|
| 出现 `TEST:FAIL`、`TEST:FAULT`、`OS ASSERT FAILED` | 失败 | 1 |
| 出现 `TEST:PASS`，且之后 0.5 秒内（`GRACE`）没有出现上述失败标记，且 `--expect` 文本按顺序出现 | 通过 | 0 |
| QEMU 在出现 PASS 之前就退出 | 失败 | 1 |
| 超时仍没有结论（包括完全无输出） | 超时 | 2 |
| QEMU 无法启动 | 错误 | 3 |

**设计要点**：超时、无输出、异常退出都不会被当作通过；`GRACE` 观察期用来发现“先打印 PASS、随后崩溃”的假通过。

### `scripts/run_all.sh`

用例清单：`pos` 表示正例（必须通过），`neg` 表示负例（运行脚本必须给出指定的退出码）。构建失败也算失败。

### `target/negative/neg_*.c`

| 编号 | 文件 | 行为 | 脚本应给出 |
|---|---|---|---|
| NEG-01 | `neg_hang.c` | 无输出，死循环 | 超时，退出码 2 |
| NEG-02 | `neg_fail.c` | 输出 `TEST:FAIL` | 失败，退出码 1 |
| NEG-03 | `neg_fault.c` | 执行 `udf` 触发 HardFault | 失败，退出码 1 |
| NEG-04 | `neg_pass_text_only.c` | 先输出 `TEST:PASS`，随后 `udf` | 失败，退出码 1 |

**意义**：这 4 个程序本身就是错的，它们存在的目的是检查“检查工具”。如果脚本会把其中任何一个判成通过，所有正例的结果都不可信。

## 5. 其他
