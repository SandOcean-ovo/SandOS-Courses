# 阶段 2：排错记录

## 1. 初始化后仍保留旧 count

用 0xa5 填满 OS_Sem 后调用旧 OS_SemInit，等待表正确清空，但 count 没有变成规定的初值。零初值、非零初值及后续消费断言失败；不是构建问题。原函数只调用 List_Init，没有给 count 赋值。现显式接受 uint16_t init_count，并在发布对象前赋值。不能用静态对象恰巧初始为 0 代替这项验证。

## 2. task/ISR post 在上限回绕

测试独立把 count 设置为 UINT16_MAX-1，一次 post 正确达到上限，下一次却返回 OS_OK，count 也不保持上限。原两条路径都直接 count++。现无等待者且达到上限时返回 OS_ERR_OVERFLOW；任务版在原临界区内拒绝，ISR 版先拒绝再接触输出标记。重复失败仍必须保持上限。

ISR 原实现会清除输出，因此“溢出失败保留 TRUE”以及后续 NULL 参数保留 TRUE 的组合也失败；本轮将溢出检查置于输出写入之前。成功路径累积标记问题没有顺带修复。

## 3. GDB 异常返回检查偶发失败

完整回归首次失败在 old_task_exception_return：其余 36 项通过。首次失败没有保存当时 ICSR，所以不能断言它必定与后续实验同源。

随后确定置起 SysTick，复现相同检查失败：before_return ICSR=0x0400f80e，after_return PC=0x000000e8、xPSR=0x2100000f，异常号 15。停掉 SysTick CTRL 不会移除已挂起请求，单步后观察到了 SysTick 处理程序，原检查却期待任务寄存器。

现仅在原本就暂停 tick 的单步窗口补写 PENDSTCLR（位 25，0x02000000）。同样确定置起后通过，after_return PC=期望任务 PC；原寄存器比较保持不变。两个 SEM 用例和 GDB 用例随后各重复 5 次通过。

位定义可核对项目内 CMSIS 6.1.0 的 `third_party/cmsis/core_cm3.h`：PENDSTSET 为 bit26，PENDSTCLR 为 bit25。此测试干预不验证并发中断正确性；没有改内核以回避失败。

## 2026-11-08 互斥锁：复现与定位

1. MUTEX-01 在旧实现的 10 项检查中失败 2 项：H 接锁后 State 仍为 BLOCKED；HH 后续竞争时，继承分支只改 H 的 Priority，不摘旧就绪节点，导致 Priority=1 但节点仍属于 ReadyList[2]。复现程序在检查到不一致后结束，避免继续释放时破坏链表。修复在交接时先设 READY，再入就绪表，最终新增直接持锁归属的检查。
2. MUTEX-02 在旧实现的 9 项检查中失败 2 项：第 256 次 Pend 返回成功，uint8_t NestCount 从 255 回绕为 0。改为加一前拒绝，返回既有 OS_ERR_NESTING；没有改大类型来掩盖边界。
3. 仅修前两点后，MUTEX-01 已通过；MUTEX-02 又暴露第二把锁的等待环：见证任务已持 other 后再等待 owner 的 mutex，owner 随后又尝试 other，形成环。日志先报告 busy_second_lock_returns_without_blocking FAIL，随后明确超时。M1 通过每任务一把 HeldMutex，在任何副作用前拒绝第二把不同锁；不是实现多锁继承或声称任意死锁均已解决。

失败证据依次保存于 `tests/build/mutex-20261108/` 的 `MUTEX-01-before.log`、`MUTEX-02-before.log`、`MUTEX-01-partial.log`、`MUTEX-02-partial.log`。全部由真实 QEMU 任务执行，不是主机模拟切换。

## 2026-11-08 Git Bash 下主机新编译无诊断失败

本轮首次完整回归有 24 项符合预期，仅 HOST 编译失败；GCC 返回 1 且没有具体源码诊断。PowerShell 直接重编译成功，但 Git Bash 内强制重编译仍失败，因此没有用旧 EXE 的运行结果掩盖问题。

检查同一 GCC 的 -v 输出，失败止于 cc1；Git Bash 启动后把自身 `/mingw64/bin:/usr/bin` 放到了指定 UCRT64 目录之前。在 Bash 内重新设置测试工具优先级后，强制 `mingw32-make -B -C tests/host all-build` 和主机正／负测试通过，最终完整 25 项通过。已修 run_local.ps1 的环境边界。具体哪个 DLL 或前端依赖发生冲突未独立断言；日志只支持 PATH 顺序相关的定位，不写成内核编译错误。

证据：`full-suite.log`（首次失败）、`host-forced.log`（Bash 内仍失败）、`host-bash-diagnostic.log`（路径／前端现场）、`host-path-fixed.log`（强制重建与主机套件成功）、`full-suite-final.log`（最终 25 项通过），均位于同一日期目录。

## 2026-11-12 阻塞 API 上下文

1. **可用资源也被非法调用消费。** 在基线 487470a 上运行 CTX-01，双层用户临界区的第一组就出现 semaphore／mutex／queue／memory 返回检查失败和快照不变检查失败，共 5 失败。原因是旧入口直接进入自己的临界区并走快路径，没有拒绝调用者上下文。不能只在资源不足时检查，否则“偶尔不阻塞”会掩盖误用。修复公共入口后，六种上下文、两组条件完成 74 检查。
2. **Delay 误用未到断言。** 基线 CTX-02 在 3 秒内未到 OS_AssertFailed，运行器退出 2；此结果不能算通过。旧实现已改变延时队列，但 PendSV 被调用者屏蔽。修复后不改生产断言，GDB 在真实断言入口核对 9 项状态；SVC 和 Delay(0) 同样通过。
3. **测试观察内部计数的声明遗漏。** 最初 CTX-01 编译缺少 g_CriticalNesting 声明；增加测试专用 extern 后才运行基线复现，不把编译失败当内核缺陷。
4. **非交互 Bash 缺少基础工具路径。** 本轮首次完整入口报 cygpath／dirname／mkdir command not found，后续构建日志目录因而不存在，汇总 failures: 30。Git Bash 启动时 PATH 没有 /usr/bin；只修工具链优先级仍不足。入口先显式补 /usr/bin，再转换和排列本机工具目录，第二次完整执行 30 项通过。原始日志保存在 full-suite-path-failed.log；没有隐藏失败或跳过测试。

限制：这次拒绝路径只读屏蔽寄存器，不修正现有最外层 ExitCritical 无条件开中断的问题；在合法阻塞测试中只使用规定的普通线程上下文。

## 2026-11-12 临界区状态恢复

**现象与复现：** CRIT-01 在 d098444 上 18 检查中失败 2 项，均为进入前 PRIMASK=1，最终退出却读到 0；正常进入和内层退出检查可通过。测试运行器看到 TEST:FAIL 后退出 1，未当作成功。

**原因：** 旧 ExitCritical 在全局嵌套计数归零后固定调用 OS_Enable_IRQ，没有记录最外层原屏蔽。只保留计数能避免内层过早开放，却不能区分调用者原本已经关中断的情形。

**修复与教训：** 先取得旧 PRIMASK 并屏蔽，再在计数为 0 时保存该原值；最后退出恢复原值。独立 ISR 局部保护不修改任务计数。CRIT-02 用真实 SVC／IRQ0 检查 pending IRQ 不能在内层退出时运行，避免只读计数就宣布中断行为正确。新负例确认 ISR 误用任务接口和未配对退出仍由生产断言报告。

**边界：** 当前不是 NMI／HardFault 安全内核；禁止在保护期间手动开中断、阻塞、切换任务或错序恢复原值。新增函数尚未接入所有 FromISR 路径，不据此声称 ISR API 已全面修复。

## 2026-11-12 ISR 累计标记与调度

**已复现的标记覆盖。** 旧 FromISR 在成功或部分失败路径写 FALSE。最初连续复用标记的检查产生 14 项失败，其中后面的溢出／NULL 分支受之前失败连带影响；为隔离具体错误，测试改为每项独立预填 TRUE，再在同一旧内核运行。最终 22 检查中 10 失败，准确对应两种屏蔽场景中的 semaphore 无等待成功、queue 发送成功／满失败、queue 接收成功／空失败。初稿日志保留为 ISR-01-before-initial.log，不把连带失败说成独立内核缺陷。

**缺少 ISR 尾部调度入口。** 旧代码唤醒后仅更新就绪表／标记，缺少公开 YieldFromISR。新增入口按最新全部就绪状态重选，使用真实非 tick 异常验证，不依赖下一次 SysTick 帮忙。IRQ0 抢占 SVC 后外层再次重选，仍选 H，不回退为外层先前选中的 M。

**共享结构的另一条更新路径。** 静态阅读发现 SysTick 修改相同链表且可被更高优先级资源 ISR 抢占，不能仅保护 FromISR。补独立保护后，GDB 在 tick 更新窗口软件挂起 IRQ，观察 PRIMASK=1，IRQ 恢复后才执行并看到完整状态。该竞争风险来自静态分析，未宣称已在原内核复现随机链表损坏。

**验证边界。** 原启动窗口断言未被删除。未把队列复制大小泛化为恒定中断延迟，也未新增阶段 2B 阻塞发送、超时或 NMI／HardFault 内核调用。新增同／低优先级用例通过后再重跑全套，不把首轮 39 项结果冒充最终 40 项。
